# OpenOmsi + BBS 2.1.0 — PeDePe native integration

## Why 2.1.0 exists

On 9 October 2026 PeDePe released the first official **OpenOMSI (Beta)** integration for Bus Company Simulator / Busbetrieb-Simulator. BBS now launches openOMSI with the selected map, bus, time/timetable and driver context and performs the normal trip completion/evaluation flow itself.

The 2.1.0 release therefore stops trying to replace that work in the recommended mode. It keeps the project focused on the features that PeDePe still does not provide: the **company multiplayer layer**, **HostAgent**, **CompanyHost**, automatic per-map dedicated servers, Cloudflare/public addresses, company clock and the server compatibility adapter.

## Recommended mode: PeDePe native + our multiplayer

1. Extract the complete 2.1.0 package.
2. Open **Setup.exe** and configure the original OMSI 2 folder and the **real** `openomsi.exe` as before.
3. If the company multiplayer is used, keep it enabled and select/import the same company profile used in 2.0.5-dev.4. The HostAgent/server configuration is intentionally compatible with the existing profile.
4. In BBS/BCS select **OpenOMSI (Beta)** as the program used for the trip.
5. For BBS's OpenOMSI path, select the package folder **`PeDePeAdapter`**. That folder contains a drop-in `openomsi.exe` built from this repository.
6. Start the trip normally in BBS.
7. Finish through BBS's normal **Terminate/Finish tour** action. In this native mode, do **not** use the old manual F9 bridge procedure.

The BBS command line is treated as authoritative. The 2.1 adapter forwards PeDePe's arguments unchanged to the real openOMSI executable and, only when a configured company session is required, appends:

```text
--lan-join <company session address> --lan-name <player name>
```

Unknown/new PeDePe arguments are preserved. This means new map, bus, timetable, driver or evaluation options do not need to be reimplemented by the bridge.

## Future-proof networking handoff

If BBS/openOMSI later starts the trip with its own `--lan-join`, 2.1.0 detects that and **does not append a second multiplayer destination**. Probe/menu/server launches (`--help`, `--version`, `--server`) also pass through without company injection.

## Server and HostAgent

**They remain.** 2.1.0 retains the 2.0.5-dev.4 server architecture:

- `HostAgent.exe`;
- `CompanyHost.exe`;
- automatic per-map session selection;
- company profile and invite/profile links;
- company clock/date handling;
- `/status` validation before the client enters;
- selected official openOMSI dedicated server support;
- bundled compatibility server;
- Cloudflare/tunnel support;
- protocol-6/free-player-bus compatibility work from 2.0.5-dev.4.

The PeDePe adapter calls the existing multiplayer planner. It can wake the matching HostAgent session, validates map/date/time/protocol/player capacity, and only then launches the real openOMSI with the company join parameters.

If multiplayer is enabled but the matching company session cannot be prepared, the adapter deliberately **blocks the trip instead of silently opening single-player**, because that could produce a BBS trip record that was supposed to be multiplayer.

## Legacy fallback

The historical `Omsi.exe` interception/BCS facade remains in the package for compatibility and regression fallback. It is no longer the recommended path when the current BBS OpenOMSI (Beta) option works.

This is useful while PeDePe's new integration remains beta, particularly because early community reports still mention incomplete evaluation categories, traffic-light detection, follow-up-tour handling and OpenOMSI-mod visibility.

## Diagnostics

Native-mode launches write:

```text
app/pedepe-native-v2.1.log
```

The Setup diagnostics ZIP now includes this file when present. Package verification also requires `PeDePeAdapter/openomsi.exe`.

## Important test boundary

Automated source, Windows build, package-integrity, Defender and argument-forwarding tests can verify the adapter itself. A **real BBS account + real PeDePe native trip + real openOMSI client** is still required for the final live validation of trip start, evaluation and follow-up behavior because those vendor products/services cannot be reproduced in CI.
