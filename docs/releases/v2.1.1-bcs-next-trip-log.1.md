# Optional BCS next-trip communication update

The observed BCS build accepts a continuation trip inside its Java process and
logs only `Weitere Tour Multiplayer` or `Weitere Event Tour Multiplayer`. This
path bypasses the initial launch screen, so it does not emit the next shift ID,
map, line, tour or departure and does not relaunch the PeDePe adapter. The
`native-live-next-trip-1` monitor detects completion but cannot see the selected
continuation. This is a missing event payload, not ZIP order.

This separate, reversible updater modifies only `bbs/f.class` in the exact
inspected, unsigned local JAR. It appends the already accepted `system.I` shift,
map and trip description to those two log events, only for BCS multiplayer
using its native openOMSI mode. Other logs and the existing logger are retained.
It does not modify authentication, purchases, web services, selection logic,
personnel files, evaluation logic, gameplay, timetable or IBIS directly. The
existing adapter performs its stable-state checks and native confirmation.

The updater checks the full original JAR SHA-256, verifies every new ZIP entry
and the exact contents of every unchanged entry, preserves a byte-identical
`.antes-proxima-viagem.bak` backup, then replaces the JAR. Unknown builds and
conflicting backups are refused. A second application is a no-op. Close BCS
and the game first; no host or player ZIP needs reinstalling.

To build, use a JDK with compiler and internal ASM modules and Go 1.23.2:

```
python3 scripts/build_bcs_trip_log_patch.py /path/to/the/inspected/local.jar \
  --go /path/to/go --output /path/to/Atualizar-Proxima-Viagem-BCS.exe
```

The vendor JAR and generated `source/bcs_trip_log_patch.bin` are not repository
content. The build script obtains the one logger class from the supplied JAR.
The updater is optional and intentionally excluded from normal full-package
builds; its portable preservation tests are included in source checks.

Validation: the actual modified logger was loaded with `-Xverify:all` and
exercised against isolated accepted-state fixtures; event, ordinary continuation,
unrelated log, incomplete state and legacy backend paths were checked. The
produced metadata is accepted by the existing adapter parser. Archive tests
check backups, content preservation, idempotency and rejection. A Windows BCS
session must still verify the complete timetable/IBIS change. Official BCS
updates may replace the local logger; a new JAR must be inspected independently.
